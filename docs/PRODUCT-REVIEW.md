# StarRank 产品分析：怎样做得更好

> 写于 2026-10-13，与 [REDESIGN.md](REDESIGN.md)（架构）配套。本文只谈产品：用户为什么来、为什么再来、
> 为什么替我们传播。依据是今天实际浏览线上站点（首页 / 详情页 / 应用商店 / 开发者榜 / 爆款榜）
> 的观察，加上 `STRATEGY.md` 的既定方向。没有 GA 数据，所以流量侧只能从结构判断。

---

## 一、一句话结论

**站点现在是"六个都做了一点的展示站"，而它唯一能赢的位置是"开源热度的可信信号源"。**
今天线上的增长榜、爆款榜、开发者榜、应用商店"上升"榜，头部全被刷 star 的仓库占据。这意味着
规划里排第一的护城河（star 质量检测）已经不是"锦上添花"，而是"没有它，站点最有差异化的几个
页面正在替刷榜者做广告"。其余问题（首页不变、分类页不可索引、没有回访理由、品牌不一致）都
重要，但都排在它后面。

---

## 二、线上观察到的事实

### 2.1 增长类榜单已被刷榜仓库占领

今天（2026-10-13）看到的：

| 页面 | 头部条目 | 疑点 |
|---|---|---|
| 爆款榜·周 | `morluto/rea` 一周 +130.5k，总 157k | 一周内从 2.6 万涨到 15.7 万 |
| 爆款榜·周 | `boykopovar/AnyPS5` 一周 +27k，总 33k | "自动移植 PS5 可执行文件到 Linux"，一周 2.7 万 |
| 应用商店·上升 | `storytold/` 名下 8 个仓库，每个"纯 Rust 从零重写 Photoshop / Word / Excel / Premiere…"，各 +1k 到 +6k/天 | 同一账号批量 |
| 开发者榜·上升 | 第 1 名 1 个仓库、+2.4k/天、无 X、无简介 | 单仓库单日爆发 |
| 首页趋势条 | 上述几个全在 | 首页第一眼看到的就是它们 |

不需要算法就能看出异常，但站点把它们放在最显眼的位置，还配上"🔥"。一个声称帮人发现"真正在
涨什么"的站，现在的表现比 GitHub 官方 trending 更差：官方榜至少没有"上升第一"的标签背书。

### 2.2 首页默认榜一年不会变

首页默认是全时 star 总榜：build-your-own-x、awesome、public-apis、freeCodeCamp……前 24 名里
14 个是清单/教程/面试题。这个列表所有人都知道，明天也不会变；用户没有理由第二次打开首页。
change 12 专门做了 type 分面来区分"资料"和"软件"，但产品决定默认全显示，等于没做。

### 2.3 分类页不是真正的页面

57 个领域节点、8 种形态、11 种语言筛选，全部是 `?category=ai/agents` 这样的查询参数。
搜索引擎不会把它们当独立页面收录，于是"best open source AI agent frameworks"这类长尾搜索
无法落到我们这里。这些本应是站点最大的 SEO 资产（`STRATEGY.md` 把 SEO 长尾列为增长方向之一），
现在是零。`/apps/best/<shelf>` 是唯一做对了的例子。

### 2.4 没有任何回访回路

没有 RSS、没有邮件、没有"关注某个分类"、没有"上次来之后有什么新东西"。每个页面都是
一次性消费。`STRATEGY.md` 自己指出目录类产品的留存通病是"静态清单"，解法是"动态榜"，
但动态榜在没有"订阅"动作时留存仍然是零。

### 2.5 详情页是最好的页面，但停在"看"

名次行（Overall #13 · Shell #2 · AI Coding Assistants #2）、增长曲线、README、下载按钮，做得好。
缺的是"动作"：没有徽章可复制、没有"为什么在涨"、没有作者其他项目和 X、没有仓库创建时间
（数据库没存）、没有同类对比。用户看完只能回 GitHub。

### 2.6 细节损耗信任

- 浏览器标签页标题是 `… · GHTA`，内部代号泄漏到品牌位；页头写 "StarRank Explorer"。
- 应用商店卡片图标大面积空白（图标覆盖 6,695 / 18,639）。
- 六个一级入口（排行 / 爆款 / AI / 应用 / 开发者 / 洞察）每个都薄，加上 HF 模型榜，
  访客看不出这个站"是什么"。
- GA 为空，所有产品判断没有数据。

## 三、重新定位

**从"GitHub 排行站"改为"开源项目热度的可信信号源"。**

对用户的承诺压成一句：**我们告诉你什么在真涨，什么是刷的。** 这句话同时满足三件事：

- 差异化：OSS Insight / star-history / bestofjs / GitHub trending 都不做真伪判断；
- 传播：每周一篇"本周刷榜仓库"天然是爆款内容（规划里早就写了）；
- 变现：VC 尽调、技术选型愿意为"真实增长"付费，为"又一个榜单"不会。

所有页面围绕这句话重排：首页回答"今天什么在真涨"，分类页回答"这个领域什么在真涨"，
详情页回答"这个项目的涨是真的吗、为什么涨"，开发者榜回答"谁在真做东西"。

---

### 三·补：多源是信息架构的根基

后续要接 iOS / Android 应用榜、Chrome / Edge 扩展榜。它们不是"往 GitHub 站上多挂两页"，
而是要求**源是一等维度**：

- **导航按源分**：GitHub · 应用商店 · 浏览器扩展 · 模型 · 今天在涨（跨源）。找 iOS 榜的人不看
  GitHub，受众不重叠，放一个入口下只会互相稀释。每个源自己的分类树、指标、URL 前缀
  （`/github/c/ai/agents`、`/ios/c/productivity`、`/chrome/c/developer-tools`）。
- **指标与信号是槽位**：star / 下载 / 名次 / 用户数，增长表达为 "+1.8k ★" / "上升 12 名" /
  "+40k 用户"。条目行、信号标签、详情页主体都按源换内容，模板只有一套。
- **"可信信号"跨源成立**：刷 star ↔ 刷评分 ↔ 刷用户数，同一套 A 到 D 档，定位不用改。
- **开源应用商店是跨源枢纽**：货架树按用途分，iOS 应用、扩展、开源桌面应用都落进同一棵树，
  "Notion 的开源替代"自然扩展为"Notion 的 iOS 替代 / 扩展替代"。这是多源之后最大的产品增量。
- **国家是新维度**：商店榜按国家出，要与界面语言分开选择。

## 四、要做的事（按优先级）

### P0 · star 质量分（两到四周，架构阶段 0 拆出 worker 后开工）

最小可行版本不做全量，只做**进过任何增长榜的仓库**（每天几百个）：

1. 采样 stargazer：GitHub API `stargazers` 带时间戳，每仓库取 300 到 500 个（最近的优先）。
2. 特征：账号年龄分布、粉丝为 0 比例、无公开仓库比例、star 事件按小时聚集度、
   同一批账号是否同时 star 了另一批可疑仓库（账号共现）。
3. 输出 `labels.starQuality`：A/B/C/D 四档加一个"可疑"标记，附三条可读理由
   （"68% 的 star 来自注册不到 30 天的账号"）。
4. 应用：增长榜、爆款榜、开发者榜、应用商店"上升"默认**只排 A/B**，C/D 折叠到"查看被过滤的
   N 个"；详情页显示档位和理由；徽章只发给 A/B。
5. 内容：每周自动生成"本周可疑爆款"草稿，人审后发。

这一项同时解决 2.1 的榜单污染、规划里的传播爆点、变现信号，是全站杠杆最大的一件事。
它依赖 `REDESIGN.md` 阶段 0 的独立 worker（长时间跑、几万次 API 调用）。

### P1 · 把分类做成真实页面（一周，可立即做）

- `/c/ai/agents`、`/c/ai`、`/l/rust`、`/t/cli` 这样的路由替代查询参数，每页独立标题、描述、
  `canonical`，进 sitemap。57 + 8 + 11 ≈ 76 个长尾落地页。
- 页面结构固定：本领域本周真涨 Top 10（P0 过滤后）→ 本领域总榜 → 本领域活跃开发者。
- 现有 `?category=` 做 301 跳转。

### P1 · 徽章（三天，依赖架构阶段 2 的名次落库）

`/badge/{owner}/{name}.svg`：显示"AI Agents #4 · ↑3 this week"，明暗两版，详情页一键复制。
只发给 A/B 档，徽章本身就带"真实增长"背书，这是 star-history 的曲线徽章给不了的东西。

### P1 · 首页改为"今天"视角（一周）

- 默认不再是全时总榜。首页分三块：**今天真涨的**（按领域各取 3 个，P0 过滤）、
  **本周新进入前 1000 的**、**领域热度**（现有热力图缩成一行）。全时总榜降为一个 tab。
- 增长榜默认排除 awesome / tutorial / interview 三种形态，资料类单独一个"资源榜"。
- 标题改成 StarRank，去掉 GHTA。

### P2 · 回访回路（一到两周，依赖架构阶段 2 的 `boards_history`）

- 每个分类页一个 RSS（真涨 Top 10 周更），零登录。
- 周报邮件：一封全站 + 按领域订阅；用 Buttondown 之类的托管服务，不自建发信。
- 详情页"自上次访问以来"用 localStorage 做轻量版，不需要账号。

### P2 · 详情页补"动作"

- 徽章复制、作者卡片（其他仓库、X、公司）、star 质量档位、同类项目（同 `labels.domain`
  按质量分取 6 个）、创建时间（抓取时补 `gh.createdAt`，现在没有）。

### P2 · 应用商店与开发者榜的净化

- 应用商店"上升"按质量分过滤；同一 owner 一屏最多出现 2 个；图标缺失时用首字母色块而不是空白。
- 开发者"上升"要求至少 2 个仓库或 A/B 质量档；把 X 账号提到行首，这是唯一能让上榜者主动
  转发的元素（"我是本周 AI builder 第 3 名"）。

### P3 · 收敛一级导航

六个入口收成四个：**排行**（含分类、语言、形态）、**今天在涨**（爆款 + 可疑榜）、
**应用**（商店 + 替代品）、**开发者**。AI 生态、话题、热力图并入排行的二级；HF 模型榜在有
GA 数据前降为二级入口，流量证明价值后再升回来。

### P0 的前置：打开 GA（一天）

`deploy/release.env` 填 ID 重新构建前端。没有数据，以上所有优先级都是猜的。

## 五、内容策略的调整

`CONTENT-ROADMAP.md` 的选题都对，但执行方式要改：

- 从"写文章"改成"固定栏目 + 数据自动生成草稿"。两篇文章用了三个月，说明手写不可持续。
- 三个固定栏目：**本周可疑爆款**（P0 产出）、**本周真涨 Top 20 按领域**（`boards_history` 产出）、
  **月度领域报告**（热力图 + 新进前 1000）。每篇模板固定、数据块实时，人只写 200 字判断。
- 一次性深度文章只保留 T22（star 通胀）和 T23（方法论），各写一篇作为"镇站之作"。

---

## 六、不做的事

- 不做登录、收藏、评论。回访用 RSS 和邮件解决，账号系统在这个阶段只增加攻击面。
- 不扩新数据源（Chrome / App Store）。先把 GitHub 一个源的"真伪"做成权威。
- 不做 AdSense。先有流量数据再谈。
- 不追求 8 语言内容对等。界面保持 8 语言，内容只做中英。

---

## 七、顺序与架构的对应

| 产品项 | 依赖的架构阶段 | 可开工时间 |
|---|---|---|
| GA、品牌标题、分类真实路由、首页重排 | 无 | 立即 |
| star 质量分 | 阶段 0（worker） | 阶段 0 完成后 |
| 徽章、详情页名次 | 阶段 2（ranks 落库） | 阶段 2 |
| RSS / 周报 / "上升 N 名" | 阶段 2（boards_history） | 阶段 2 |
| 同类项目、作者卡片 | 阶段 3（labels 归一） | 阶段 3 |

两条线并行：架构按 REDESIGN 走，产品先做"立即可做"的四件事，等 worker 一拆出来就上
star 质量分。

---

## 八、要你拍板的

1. 定位是否接受改为"可信信号源"，并以此收敛导航（第三、四节 P3）。
2. star 质量分的处理方式：**折叠**可疑仓库（建议）还是**标红但保留排名**。折叠更干净但会被质疑
   "凭什么"；标红更稳妥但首屏仍然难看。
3. 周报用托管服务（Buttondown / Resend，有少量月费）还是先只做 RSS。
4. HF 模型榜是否降级为二级入口。
