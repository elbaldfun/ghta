## 一、定位与核心矛盾

**现状**：starrank.dev 是一个 GitHub 高星仓库的排名/发现站——8 语言、67k repo、66% 已归类、日增长数据、2 万仓库有十年 star 曲线、博客 + 统计端点齐全、后端在 droplet。

**核心矛盾**：纯展示层面，OSS Insight / star-history / bestofjs 都做过。**目前没有护城河。** 差异化必须来自**别人没有的信号**，不是又一个 trending 列表。

**战略主线（贯穿全文）**：
```
差异化信号  →  流量  →  变现
```
三步有严格先后。**现在跳过前两步谈变现，做什么都收不到钱。**

## 三、方向一：增长 / 流量（当前最该投入）

本品类的铁律：**能嵌入 README 的东西会自己传播**。star-history 整个站就是靠这个起来的。

- **🚩 可嵌入的排名徽章（旗舰）**：作者把徽章贴进自己 repo 的 README = 每次浏览都给你免费曝光 + 反向链接。
  - **必须按"排名/上升"做，不要克隆 star 曲线**（那块 star-history 赢了）。"AI 分类第 12 名""本周上升 3 名"这种荣誉感是钩子，且**只有你有**。
  - 技术：SVG（矢量、小、可明暗两版），`GET /badge/{owner}/{repo}.svg`，长缓存，只给已追踪 repo 生成（防滥用）。
  - **诚实前提**：徽章是"有了初始流量后的放大器"，不是 0→1 的第一推动力——冷启动阶段没人知道你，也就没人来挂。
- **SEO 长尾**：67k repo 详情页 + 博客，复利资产，慢热。
- **HN / Reddit / X**：适合发数据分析文章（如已发的 T20），一次性尖峰。
- **⚠️ 公众号 / 小红书**：是围墙花园——正文不能放外链，是"站内内容产品"的好渠道，是"引流回站"的坏渠道。做内容号可以，别指望导流。

## 四、方向二：差异化 / 护城河

- **🚩 刷 star 检测 / star 质量分**：一个功能同时解决四件事——① 社媒选品的"防翻车关卡" ② 传播爆点（"这个爆火项目 40% star 是刷的"能疯传） ③ **唯一有人付钱**的信号（VC 尽调、选型） ④ 博客独家选题。市面上几乎没人认真做。**这是最强的支点。**
- **归类导航**（已 66%）：已是 vs 纯 trending 站的差异点，值得打磨。
- **开发者图谱**（repo→背后的人）：见方向三，是很多东西的地基。

## 五、方向三：开发者 + X 关联（"值得关注的人"）

本会话讨论最深的方向。**愿景对、价值真，但"抓 X 用户"的naive做法是钱坑。**

### 5.1 价值（真实且差异化）
技术影响力活在两张图：GitHub（谁在写代码）+ X（谁在制造话题）。连起来 = "谁在技术圈重要、他在写/押注什么"的统一图谱。**没人做好过**，正好是 VC 付费意愿最高的场景。含金量排序：
1. **早期信号**：有影响力的 X 账号悄悄开新 repo / 力捧某项目 → 比 GitHub trending 更早。
2. **可信度背书**：repo 卡片加"作者 @xxx，5 万粉，前 OpenAI"。
3. **内容燃料**："本周被大佬 star 的新项目" = 社媒爆款素材。

### 5.2 三个硬骨头
1. **身份关联是命门且很脏**：靠名字匹配极不可靠。唯一干净的信号是**用户自声明**——GitHub 用户 API 的 `twitter_username` 字段。高精度但覆盖不全。**连错人是灾难性的。**
2. **X 官方 API 贵到离谱**：Pro 档 $5,000/月，官方 API 也**没有"周/月增长"字段**。
3. **"有价值的 X 用户"怎么定义**：没有干净 API，得有种子再爬。

### 5.3 第三方 API 评估（twitterapi.io / SocialData / Apify / Bright Data 等）
这些是 **scraping-as-a-service**，按量计价（约 $0.1–0.5/千条），把 X 从"碰不起"变成"targeted 场景用得起"（几十刀/月）。**但代价从钱换成了合规和稳定性**：
- **ToS/法律风险只是转移**：它们违反 X 条款在爬。provider 会被封杀（数据管道会不可预测地断）；**转售爬来的数据法律暴露最大**。
- **稳定性差**：和 X 反爬是猫鼠游戏。

| 场景 | 判断 |
|---|---|
| 内容素材（周更"大佬 star 了什么"） | ✅ 用，断了不影响 |
| 富集开发者层的 X 粉丝数 | ✅ 用，配合 GitHub 自声明 |
| 200 个人工种子账号动态 | ✅ 用，量小可控 |
| 做成常在的核心产品支柱 | ⚠️ 慎，依赖脆弱 |
| 打包 X 数据卖给 VC | ❌ 别，法律暴露最大 |

**聪明架构**：让 GitHub 提供【身份】（自声明 twitter，免费+合规），第三方 API 只补【已知 handle 的公开指标】——绕开最贵最脏的身份识别与图谱爬取。

### 5.4 "值得关注的开发者"目录产品
把独家资产（GitHub↔X）变成产品本身。**需求真**（"我该在 X 上关注谁"高频）。但两条铁律：
1. **必须按实绩排，不能按粉丝排**。按粉丝 = 大路货、没人信。**"某领域最能造东西的人，顺便这是他的 X"** 才是护城河——把常见的虚荣指标目录整个反过来。
2. **老实定位成"技术圈/开发者"，别吹全行业**。你只认识会写代码的人；设计师/VC/财经 KOL 没 GitHub 实绩，你零信号。
3. **做成动态榜**（"本月新晋""谁在涨"）而非静态清单——解决目录类产品的留存通病。

**冷启动很容易**：种子 = "做过高星 repo 且自己填了 twitter 的开发者"，GitHub 免费送，且这两个条件本身就筛掉噪音。

**实测种子密度**（抽样前 50 高星 repo 的 owner）：
- 独立 owner 49，其中**组织 59%、个人 41%**（头部高星多是公司）
- 个人里 **42% 填了 twitter**，粉丝中位数 **17,294**（都是真大神：sindresorhus/mattpocock/trekhleb…）
- 全盘估算：44,988 owner → 保守 ~2.2 万个人 → **约 8,000–9,000 个已声明 X 的开发者种子**。对"AI/技术圈该关注谁"绰绰有余。
- **注意**：排名主体必须先过滤掉 Organization（GitHub `type` 字段能干净区分）。

### 5.5 行业扩张原则
"一个行业一个行业做"方向可以，但**错在按什么扩**：
- **每加一个没有实绩信号的行业，就把自己稀释成"按粉丝排的大路货"一次**。
- 正确做法：**每个行业自带一个"实绩信号源"**——开发者=GitHub，AI 研究者=arXiv/Scholar，Maker=Product Hunt，设计师=Dribbble，Crypto=链上+GitHub。保持"用真实作品排名"的统一内核。
- **先深后广，沿信号扩，别沿行业铺**：先把"开发者/AI 圈该关注谁"做成权威（AI 是当下注意力最集中、付费意愿最高的赛道，不嫌窄），再扩相邻的可复用信号垂直。**别跳到离你很多圈的行业**（时尚/财经），那里只能按粉丝排 = 自杀。

### 5.6 落地顺序（本方向）
```
1. 建开发者层（遍历 owner → GitHub /users/{login} → 存 type/followers/twitter_username/bio/company）
   —— 免费、合规，44,988 owner 约 9 小时跑完（或先只跑高星 owner，几十分钟出种子）
2. 用自声明 twitter_username 建关联（免费）
3. 第三方 API 补 X 侧粉丝数/活跃度（便宜，仅富集已知 handle）
4. 加 HN/Reddit 话语热度（免费 API，替代 X 的"讨论热度"）
5. 产品：按技术领域分类的"值得关注 builder + 他们的 X"（动态榜）
```
**开发者层是这一切的地基，现在不存在。**

### 5.7 本轮决策与暂缓项（2026-07-25）

**本轮开工——§5.6 步 1「开发者数据层」**：
- 建 `developers` 集合，遍历全部 **45,028** 个 owner → GitHub `/users/{login}` → 存 `login/type/name/company/bio/location/blog/followers/following/publicRepos/twitterUsername/avatarUrl/ghCreatedAt/fetchedAt`。
- **User 与 Organization 都存，靠 `type` 字段区分**——组织不丢弃，在数据层就把"公司怎么处理"解决掉（个人/公司两个产品共用这一层地基）。
- 全量一次扫（~9h），受 GitHub 5000/时限速自然分批、可断点续跑（跳过已抓的），复用 `RateLimitBuffer`。

**已讨论、本轮暂缓（记录在案，避免遗忘）**：
- **公司 OSS 画像 / "公司×领域"榜单**：价值高、成本低（复用 99.7% 分类树 + 现有 owner 聚合，一条 aggregation 即得），但排名口径与前端值得单独打磨 → 独立一轮。裸的"公司按 star 总量排"无护城河（OSS Insight 已有），不做。
- **"值得关注的开发者"排名产品**（按实绩非粉丝、过滤 Org、动态榜，§5.4）→ 数据层跑出来、验证 twitter 覆盖质量后单独一轮。
- **深度贡献者数据**（commits、`repo_contributors`、谁在贡献）：贵（逐仓库 API）且属§四"仓库质量/刷 star"护城河范畴 → 与§四一起做，本轮不碰。
- **X 侧富集**（第三方 API 补已知 handle 的粉丝数/活跃度，§5.6 步 3）→ 地基之后。

## 六、方向四：首页专区

把首页从静态排行榜变成"什么值得看"的仪表盘，改善留存（多入口=多回访理由）。**但别堆成大杂烩——挑 2-3 个高信号的做深。**

| 专区 | 就绪度 | 说明 |
|---|---|---|
| 日趋势 | ✅ 数据齐 | `dailyIncrease` 齐；未单独做首页专区（爆款横条部分覆盖） |
| 周趋势（自有快照） | ⏳ 约 07-26 | `weeklyIncrease` 数据一到自动亮；代码可先写 |
| 月趋势（自有快照） | ⏳ 约 08-17 | 同上，护城河版；GitHub 官方月榜见下行 |
| AI 热门 skills/topics | ❌（需新端点） | 从 AI 分类下 topic 聚合（llm/pytorch/chatgpt/openai…原料很好），呼应"深耕 AI 垂直"——未建 |
| **本周/本月爆款仓库** | ✅ **已上线（前端+部署）** | 扩展为爬 GitHub 官方周/月榜 `/trending/hot`，非仅 Search API；不在库的新仓库自动入库。见 §八 |
| 本周最新作者 | ❌ 需开发者层 | 与方向三同一地基 |

### 「AI 生态」专区定义（2026-07-26 锁定，宽口径）

用户找"给 AI/agent 加能力、连工具、搭智能体"的东西时是一个心智，不分我们内部的 type/domain 轴。故按用户意图框成一个 umbrella + 三支柱（并集去重 ≈ 2,480，默认按 star 增速排）：

| 支柱 | 成员规则 | 规模 |
|---|---|---|
| ① 技能 Skills | `type=skill` | 485 |
| ② MCP 服务 | `topic ∈ {mcp, mcp-server, model-context-protocol}` | 553 |
| ③ 智能体 Agents | `domain=ai/agents`（宽口径，含成品应用） | 1,765 |

- 实现走 **A（跨轴 `$or` 查询，不动分类器/不重跑）**，同话题榜的 service+缓存机制；差异化点是所有对手都缺的 **star 增速/momentum**（PulseMCP 连 star 都没有）。
- 定位：**不做"第 9 个 skill 目录"**（赛道已卷、我们 skill 数据薄），做"**本周最火的能力/MCP/agent**"——用增速切一个别人没占的角度（§一 反"又一个列表"）。
- 路由 `/ecosystem`，Header 入口「AI 生态」。

**"周/月增长"数据来源之争**：GitHub 官方 API **给不了**增长量（无历史字段）。能给的是 GH Archive（已接，但用免费 ClickHouse playground，不可靠、会 500）。**结论：首页周/月榜等自己的快照（免费+可靠+是护城河），GH Archive 只留给单 repo 详情页的深度曲线。**

**顺序**：差异化信号 → 流量 → 再变现。

## 十、技术债 / 风险（别拖成雷）

- **MongoDB 无自动备份** —— 单节点 droplet，数据丢了全没，风险最实在
- **32 个依赖漏洞**（7 critical）—— 主要是旧 NestJS package.json，清一轮
- **ClickHouse playground 会 500** —— star-history 回填不稳，要么升级源要么接受降级

- **`users` 集合 + `/user` CRUD** —— 2 条测试数据，无用途，清理可减攻击面
